## 4. 環境の約束（Python から見た形）

2026-11-12 に実装と照らして直した（下の「11/12 の直し」）。実装は `lib/core/BatchEnv.*`、`lib/core/Features.*`、`python/hasami_env/`。

```python
env = hasami_env.BatchEnv(n_envs=256, seed=1, opponent="b1",   # "b1" | "race" | "random"
                          speed_scale=1.0,                       # 機械の freeSpeed・dragSpeed に掛け、engageMs は割る
                          level="hard",          # 人間役が機械を読むときの強さ。read_actions の既定
                          capture_reward=0.2,    # 取りの報酬（1枚あたり）。11/17 の予備策で 0.5 にする
                          n_threads=0,           # 0 は CPU の数
                          track_activity=True,   # info の activity（記録用。切ると少し速い）
                          tick_ms=10)            # 内部の刻み（autoplay と同じ）
obs, scal, mask = env.reset()
obs, scal, mask, reward, dt_ms, done, info = env.step(actions)
actions = env.read_actions()                     # 今の手書きの読み（Ai の think）が選ぶ行動。評価と比べる用
```

| 名前 | 型と形 | 中身 |
|---|---|---|
| `obs` | int16 [N, 12, 7, 7] | 下の12チャンネル |
| `scal` | int16 [N, 6] | 機械の取った枚数、人間の取った枚数、残り時間（100ms単位、切り上げ）、Opening中か、人間が開始の一手を指し終えたか、speed_scale×100 |
| `mask` | bool [N, 1177] | 合法な行動。1176番の「動かない」は、Opening 中（機械の開始の一手の前）だけ偽、ほかでは常に真 |
| `actions` | int32 [N] | 行動の番号。マスクにない行動は ValueError |
| `reward` | float32 [N] | 前の決定点からこの決定点までの報酬の合計。勝ち +1、負け −1、取った枚数の差が1枚変わるごとに ±capture_reward、差が0のあいだゲーム時計の毎秒 −0.5/600。時間切れの引き分けは終わりに足すものなし |
| `dt_ms` | int32 [N] | 前の決定点からのシミュレーションの経過時間（ms、10ms刻み。Removing と Countdown の時間を含む）。割引は γ^(dt/τ)、半減期120秒 |
| `done` | bool [N] | 局の終わり。終わった局はその場で自動で reset し、`obs`・`scal`・`mask` は新しい局の最初の決定点を返す。`reward`・`dt_ms`・`info` は終わった局のもの |
| `info` | dict of arrays | `winner` int8（0 なし・引き分け・打ち切り、1 人間、2 機械）、`captures` int16 [N, 2]（機械が取った枚数、人間が取った枚数）、`truncated` bool（安全のための打ち切り。シミュレーションの時間 31 分）、`game_ms` int32（ゲーム時計）、`activity`（[N] の配列の dict: `outside` 外にいた割合、`mean_row`、`play_ms`、`threats`、`moves`、`back_forth`、`first_capture_ms`（なければ −1）、`lead_changes`）。done でない環境は進行中の局の値 |

- `step` は、時間を10ms刻みで進め（SimDriver::advance と同じ順）、機械の次の決定点で返す。決定点は、読みの時刻（`MachineController::wantsThink`。読みの間隔 `max(150, reactMs)` ごと、動かしている途中・Removing・Countdown では読まない）のうち、合法な行動が2つ以上あるもの。合法な行動が1つだけの読みでは、それを自動で指して進める。
- 座標は盤の向きのまま（r=0 が機械の一段目、c=0 が左端）。鏡像は使わない。
- 行動の番号: `((r*7 + c)*4 + d)*6 + (dist-1)`。方向 d は `Board.h` の DIR の順（0 下、1 上、2 右、3 左）。1176 が「動かない」。動かす駒の元のマスで指定し、機械は行く手が埋まれば手前で止まる（Game のルールどおり）。合法な手は今の読みの候補と同じ（クールダウン明けの駒、持ち上げ中の元のマス・保留先・確保中のマスは埋まっているとみなす、RW で壁を作るマスを通る手は除く）。
- チャンネル（値は整数。時間は100ms単位で、残りは切り上げ）: 0 機械の駒、1 人間の駒（盤上）、2 人間が持ち上げ中の駒の元のマス、3 人間の保留先、4 人間の置く間隔の残り（盤全体に同じ値。まだ置いていなければ0）、5 機械の駒のクールダウン残り、6 人間の駒のクールダウン残り、7 機械の駒の RU の残り（RU で取られうるようになるまで）、8 人間の駒の RU の残り、9 ヘッドの位置（最も近いマスに1。盤の外なら盤の端に寄せる）、10 持ち上げ中の駒の経過時間（切り捨て、元のマス。Opening 中は0）、11 RE で取られうる（空きがあと1つの）端のまとまりの駒（両者とも1。どちらの駒かはチャンネル0・1でわかる）。
- 種: 環境 i の k 局目（0 から）は種 seed + i + k×N。最初の N 局は seed, seed+1, … で、`tools/autoplay.mjs` の局の種と同じ。人間役の乱数のほかに乱数はないので、同じ種と同じ行動の列なら同じ局になる。`read_actions` で指すと、同じ種の SimDriver（autoplay）と同じ局になる（`test/test_env` で、B1 と Race の各3局の勝敗・枚数・ゲーム時計・活動が一致）。
- 11/06 計画の Step 1 のうち、この約束にないもの（人間の行動の口、観測の遅れ、推論の遅れ、読みの時刻のゆらぎ、速さのばらつき、同じ刻みの処理の順の無作為化）はこの期間には作らない。

11/12 の直し（実装の前に見つけた矛盾。ユーザーの判断で決めた）:

- Opening 中の「動かない」: 最初の約束では常に合法だったが、Opening ではゲーム時計が止まっていて時間切れが来ないので、動かないかぎり局が終わらない。勝てない相手には Opening にとどまれば報酬0のまま負けずにすむので、方策がそれを覚えるおそれがある。今の読み（`Snapshot::mustMove`）と同じく、Opening 中は偽にした。
- speed_scale: engageMs にも掛けると、1.3 の速い機械の吸着が遅くなる。速さには掛け、吸着時間は割る（1.3 で 200ms → 154ms、0.7 で 286ms）。
- 決定点ではいつも 0 の入力の差し替え: 機械は動かしている途中に読まないので、決定点にはジョブがない。そのため、最初の約束のチャンネル 4（機械が確保中のマス）と 10（機械が動かしている駒の行き先）はいつも 0、scal[4]（機械が開始の一手を指し終えたか）はいつも 1−scal[3] だった。形はそのままで、11/06 計画 3.6 にあった人間側の時間（置く間隔の残り、持ち上げの経過時間）と、人間が開始の一手を指し終えたかに差し替えた。
- 刻み: 最初の約束は100ms刻みだったが、速さはほとんど変わらず（BatchEnv と同じループの試作で、B1 相手 1スレッドの決定点／秒が 10ms で 1,054、100ms で 1,188）、読みの間隔が 250ms から 300ms に延び、autoplay や 11/06 計画の表と比べられなくなる。10ms にした。
- 取りの報酬は1枚ごと（RE でまとめて3枚取れば +0.6）。11/17 の予備策のために `capture_reward` で変えられる。
- 5章の比べる相手（今の読み）を同じ環境で動かすために `read_actions` を、局の打ち切りを区別するために `truncated` を足した。

- ランダムな方策の機械の勝ちは、B1 に 0／1,020 局、Race に 1／1,031 局、Random に 0／1,005 局（同じ設定、種 1 から）。11/17 の「Random に勝ち越す」は、ほぼ 0 勝からの出発になる。
- 方策が「動かない」を多く選ぶようになると、シミュレーションの1秒あたりの決定点が増える（ボットの読みはシミュレーションの時間に比例する）ので、決定点／秒は上がる。
