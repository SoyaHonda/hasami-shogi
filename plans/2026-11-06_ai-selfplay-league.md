# ソフトウェア計画: 面白い機械を目指して、ルールと読みを学習で作り直す

2026-11-06（専門家レビュー2回とユーザーの判断を受けて改訂。初期配置の壁は開始の一手で崩す）/ 対象: 砦をなくすルールの追加と比較、機械の読み（`Ai::think`）を自己対戦の強化学習で学習した小さなネットに置き換えること、学習の環境（C++ コアを Python から呼ぶ）、整数だけの推論（ESP32・WASM・PC で同じ手）、現実的な人間役、面白さと攻略されにくさの測り方、対局の記録。`plans/2026-10-31_ai-time-race.md` の時間の見積もり（RaceTime）と時間の競争の読みは、学習した読みが仕上がるまで既定の読みとして残す。

## 1. 背景

### 1.1 これまでに起きたこと

2026-10-31 の時間の競争による作り直しで、ボット相手に失う枚数は1局あたり約4枚から約1.2〜2.3枚に減った。ところが 2026-11-06、機械がほとんど自分から動かないことがわかった。前進の点の重みを上げると30秒で2〜3手は動くが、失う枚数はすぐ約3.7枚に戻る（つよい対 Race、100局）。何もしない人間を相手にすると、2分間一度も動かない。

### 1.2 原因: 盤端の砦

駒は両側から挟まれたときだけ取られ、盤端は挟む側になれない。そのため、盤端の段にいる駒は縦に挟まれず、盤端につながった列は横に挟まれない。機械の初期配置（一段目に端から端まで7枚）は一枚も取られず、一段目の左端から6枚並べるだけでも永久に取られない。盤の中ほどに端から端まで7枚並べた壁も、後ろに人間が回り込めないので取られない。人間の側も同じことができる。このため、勝ち負けを目的に読みを作っても学習しても、「こもって引き分け」が見つかる。読みの細かい調整では直らないので、ルールで砦をふさぐ。

### 1.3 日本将棋連盟のルールとの関係

日本将棋連盟の「はさみ将棋」の説明（https://www.shogi.or.jp/knowledge/hasami_shogi/ 、2026-11-06 に確認）には「端にいる駒の場合は、相手の動きを封じて取ることができます」とあり、図では次の3つが取った状態として示されている: 一段目の隅から3枚並んだ相手の駒を、右隣と真下の3マスを埋めて取る。左端の1枚を、上・下・右を埋めて取る。隅の1枚を、上と右を埋めて取る。隙間が1マスでもあれば取れない。今のルール（盤端に達する列は取らない、隅の囲み取りはなし）は、この点で公式と違う。盤の大きさ（7×7、各7枚）と4枚先取は実機の制作計画で決めたもので、変えない（2026-11-06 ユーザーの判断）。

### 1.4 ユーザーの判断（2026-11-06）

- 目的は「遊んで面白い機械」。攻略されにくさは、楽勝されないための最低限の条件にとどめる。
- 面白くできるなら、ルールに要素を足してよい。砦は「公式の端の取り」と「端から端までの一列の壁の制限」の組み合わせでふさぐ（第一候補）。初期配置の壁は、最初に両者が一手ずつ指すことで崩す（時計は使わない）。勝ちは4枚先取のまま。
- 強さの目安は、現実的な人間を相手に、やさしい2〜3割、ふつう5割、つよい7割以上の勝ち。
- Web のシミュレータで遊んだ対局を記録し、人間役の調整に使ってよい。
- 学習は家のデスクトップ（Windows＋WSL2 の Ubuntu、Ryzen 7 5700X 8コア16スレッド、RTX 4060 8GB）で、ほかの作業と並行できる範囲で何日でも回してよい。
- 推論の時間を測るために、開発ボード ESP32-DevKitC-32E（ESP32-WROOM-32E、無印の ESP32、4MB フラッシュ、USB シリアル変換は CP2102、Micro USB、38ピン）を注文した（2026-11-06）。届くまでは命令数の見積もりで進め、届いたら実測と ESP32 の推論の一致の確認を行う。本番の基板の ESP32 はのちに配布される予定。

### 1.5 方式の選択

| 方式 | 判断 |
|---|---|
| 手書きの見積もりと点数（今の読み） | 単独では打ち切る。学習の入力の候補と、模倣学習の出発点に使う |
| AlphaZero・MuZero 型の探索 | 同時手番・実時間に合わず ESP32 で探索できないので配る方式にはしない。PC での攻略役（3.11）に探索を使う |
| AlphaStar 型のリーグ（全部入り） | 機械と人間の両側に主役・攻略役をすべてそろえる構成は重い。学習するのは3体（機械の主役、人間の主役、主役を攻略する人間役）の小さなリーグにし、攻略されやすさの数字を見て役を足す |
| 自己対戦の強化学習（PPO）＋参照方策への KL 正則化 | 採用。magnetic mirror descent（Sokota ほか ICLR 2023、DeepNash の R-NaD と同じ系統）。ただし報酬はゼロ和でない（3.3）ので、理論の保証ではなく安定させる工夫として使う |
| 模倣学習からの出発 | 採用。今の読みと手書きのボットを真似したネットで、量子化から Web までを先に一本通す |

## 2. 目的と方針

- 機械の目的は、現実的な人間を相手に、強さの段階ごとの目標の勝率に入り、かつ自分から前に出て脅しと取りを作ること。攻略されにくさは、探索による攻略役に楽勝されないことを上限の条件にする。
- まずルールで砦をふさぐ（3.1）。取りの判定を1つの関数にまとめ、読み・ボット・LED・見積もりがすべて同じルールを使うようにする（3.2）。
- 人間役は、目標の勝率を測る「固定の基準の人間役」、学習中に機械と戦う「人間の主役」、上限を測る「攻略役」に分ける（3.5）。
- ゲームの規則と時間の進み方は今の C++ コアをそのまま使い、学習の入力の組み立ても C++ に置く。
- ネットは整数だけで推論し、PC・WASM・Python の基準でロジットまで一致させる。大きさは ESP32 の命令数の見積もりで決める。
- 学習した読みは設定で切り替えられるようにし、仕上がるまでは今の読みを既定にする。

## 3. 仕様

### 3.1 ルールの候補

すべてのルールは人間と機械に同じく効く。`Rules` の項目で切り替え、既定は今のルール（R0）のまま。（2026-11-12 ユーザーの判断）RE＋RW＋RU40 を正式なルールにした。`officialRules()`（`lib/core/Rules.h`）に1か所で定め、ファーム、Web のシミュレーター（開いたときのルール。3つとも外せる）、学習の環境がこれを使う。`Rules()` の既定は、正解表と多くのテストのために R0 のまま残す。RU20 との比較とポケットの規則の試合での確認は、行わないまま決めた。

- R0: 今のルール（基準）。
- RE（公式の端の取り）: 盤端か隅に接している駒のまとまり（縦横につながった同じ側の駒のうち、1枚以上が盤端に接しているもの）は、そのまとまりのどの駒にも、縦横に隣り合う空きマスが1つもなく、隣り合うマスがすべて相手の駒か盤端になったとき、まとめて取られる。判定するのは、相手が駒を置いた・動かし終えたとき（今の「動いた側だけがはさみ判定をする」と同じ）で、置いた駒が新しく隣り合ったまとまりだけを調べる。自分から動いて囲まれる形に入った場合は取られない。持ち上げ中の駒の元のマスと保留先は、空きマスとして扱う（持ち上げ中の駒は盤上にないため、そのマスは「動ける先」になる）。機械が引いている途中の駒は、まとまりに含めない（盤上にないものとして扱う規則のとおり）。
- RW（壁の制限と開始の一手）: ある段に同じ側の駒が端から端まで並ぶ形（壁）を作る置き・動きは反則として受け付けない（人間の置きは `Illegal`、機械の読みは選ばない）。初期配置の壁は「開始の一手」で崩す: カウントダウンのあと `Phase::Opening` に入り、両者がそれぞれ駒を1つ別のマスへ動かし終えたら Play に入る（ゲーム時計はそこから進む）。初期配置では自陣の段が埋まっていて駒は縦にしか動けないので、どの一手でも壁は必ず崩れる。Opening のあいだ、各側は1手しか指せない（2手目の持ち上げ・機械の2つ目のジョブは受け付けない）。一手ずつでは挟みも RE の囲みもできないので、取りは起きない（判定はふだんどおり行う）。取り消し（持ち上げてすぐ元のマスへ戻す）は一手と数えない。行き先がぶつかったときはふだんどおり（機械は確保しながら引き、人間の駒が先に置かれたら手前で止まる。それも一手と数える）。開始の一手で動かした駒にはふだんどおりクールダウンが付く。持ち上げ上限、置く間隔、時間切れは Opening のあいだも数えない（ゲーム時計が止まっているため。持ち上げ上限だけは実時間の 1 秒で数え、Opening でも持ちっぱなしにはできないようにする）。機械の駒は、止まると壁ができるマスには入らない（人間の駒に手前で止められても壁を作らないよう、`Game::machineCanEnter` がそのマスを断って引く駒はその1マス手前で止まり、読みも引く途中にそのマスを通る手を選ばない。2026-11-07 ユーザーの判断）。
- 第一候補は RE＋RW。予備の候補として、RU（長く動かしていない駒は、相手の駒1枚に縦横で隣に来られただけで取られる。時計は別のマスへ置いたときだけ戻り、取り消しでは戻らない。候補 20／40 秒）を用意する。RU は、RE＋RW で砦が残るとわかった場合にだけ比べる。
- LED と画面: RE で取られうる（隙間があと1つの）まとまりは、LED と画面で示す（既存の黄色の考え方を使う）。Opening のあいだは画面に「最初の一手」を表示し、指し終えた側を示す。RU の下では、両者の駒のマスを、取られうるようになる 10 秒前から緑でだんだん明るく（警告）、なったあとは水色で点滅せずに示す（2026-11-07、試遊のため。優先は反則と不一致の下、クールダウンの赤の上。`lib/core/LedPlan.h`）。Web の RU は入り切りと 20〜90 秒（5 秒刻み、既定 40 秒）のスライダーで決める。

#### ルールの比較（Step 0b、2026-11-06）

RE＋RW でも砦は残った（盤端と自分の駒で囲った、相手が入れない空きマス「ポケット」）。そこで RU（20 秒、40 秒）を加えて同じ表を作った。RU は動かない砦をすべて崩すが、今の読みは RU の脅しを読まないので B1 に大きく負ける（2026-11-07 に読みへ RU の脅しを足した。(d)）。

方法（マスは (r, c) で、r は機械の自陣の一段目を 0 とする段、c は左端を 0 とする筋）:

- 攻略役（`tools/search-exploit`、3.11）: 人間の1手（持ち上げる駒、置くマス、持ち上げる前の待ち {0, 250, 500, 1000ms}）と「1000ms 待つだけ」を単位にしたビーム探索。ビームの幅 64、深さ 6、各節点で、手の直後の局面の評価が高い 8 手（同じ駒は最初の選びで2手まで）を待ちごとに時間どおりに進める。評価は、取った枚数の差＋RaceTime の取れる見込み（機械の列とまとまりの risk×枚数、人間の列の gain。どちらも最大のもの＋残りの 1/4、重み 0.3）＋端のまとまりを囲む進み具合など（重み 0.1）−経過 1 秒あたり 0.002。ゆらぎに強い攻略（robust）は、200〜500ms 前に見た局面から（自分の手はやり直して）、機械の読みの時刻のゆらぎの種と速さ（空送り・引く速さ・吸着 ±30%）を変えた K=8 個の写しで平均して採点し、持ち上げてから置くまでを 500ms ±20% でばらつかせる。種に依存する攻略（seed）は、本物の局の正確な写し1つで先読みする（上限）。どちらも、計画を探し、最初の1〜2手を指し、また探す。1手の持ち上げてから置くまでは 500ms（読みの人間のモデルと同じ）、ルールはすべて守る。
- 砦の静的な判定（`search-exploit static`）: 機械の駒がまったく動かないとき、人間がどう指しても取れない駒を数える。人間は 7 枚で、6段目につながった空きマスのどこへでも何枚でも行けるとみなし（自分の駒どうしの邪魔も数えない）、挟みは列の両端に届けば、RE は端のまとまりの空きマスがすべて届き 7 個以下なら、RU は隣の空きマスに届けば取れるとする。取れる駒を取り除いて届く範囲を広げ、変わらなくなるまで繰り返す。人間を強めに見ているので「取れない」と出た駒は確かに取れない。1〜7 枚のすべての置き方（左右の鏡像は1回、RW では壁のある形を除く）を数えた。動かない砦が 4 枚あれば人間は 3 枚しか取れず勝てない。
- 前進を強制した読み: 前進の点の重み（`Params::advanceWeight`、出荷は 30）を 120 にした今の読み。重み 30 では開始の局面で動かず、60 以上で外へ出る（B1 相手、R0、つよい、40 局ずつ: 外にいた割合は 30 で 19%、60〜240 で 48〜60%。再現: `node tools/autoplay.mjs --games 40 --seed 1 --level hard --bot b1 --rules r0 --advance 30,60,90,120,180,240`）。
- B1: Race ボットに、考える時間（置いてから次に持ち上げるまで 1〜3 秒の一様分布、`BotParams::thinkMaxMs`）と、脅しの見落とし（1手ごとに確率 0.3 で機械の脅しを見ない: 逃げを優先せず、動かした駒の危なさと自分の列の取られる見込みを数えない、`BotParams::threatMiss`）を足したもの。
- 活動の指標（3.3、`lib/core/Activity.*`、autoplay の2つ目の表）: 外にいた割合は、Play の時間のうち機械の駒が一段目の外にいた割合（その時点の残りの駒数で割る）。脅しは、人間の列の gain が 0.5 以上になった回数（RE では、空きが1つになった端のまとまりにその空きへ1手で届く機械の駒がある場合も）、同じ形の列は1回。
- 再現: `npm run build:exploit` のあと、(a) `build/search-exploit static --rules r0,re,re+rw,re+rw+ru20` と `build/search-exploit probe --mode robust|seed --horizon 90 --per-plan 1 --rules r0,re,re+rw,re+rw+ru20,re+rw+ru40`、(b) `build/search-exploit play --mode seed --games 6` と `--mode robust --games 3`（どちらも `--rules r0,re,re+rw,re+rw+ru20,re+rw+ru40 --level hard --advance 120 --horizon 60 --per-plan 2 --seed 1`）、(c) は表の下。4コアで、(a) 静的な判定は全体で約 15 秒、probe は robust 約 6 分・seed 約 1 分、(b) は seed 約 5 分・robust 約 20 分、(c) は約 4 分。重み 30 の参考の行は同じコマンドに `--advance 30 --games 3`（robust は `--rules r0,re+rw`）。

#### (a) 砦の確認

動かない砦の静的な判定（1〜7 枚のすべての置き方）:

| ルール | 動かない砦の最小の枚数と例 | 7 枚の置き方のうち、取れない駒が 4 枚以上の形 |
|---|---|---|
| R0 | 4 枚（一段目の隅から 4 枚） | 1,168,349 / 42,958,843（2.7%） |
| RE | 4 枚（(0,0)(0,1)(1,1)(2,0) で囲んだ (1,0) のポケット） | 352,776 / 42,958,843（0.82%） |
| RE＋RW | 4 枚（同じ形。壁のある形は作れないので除く） | 352,770 / 42,958,836（0.82%） |
| RE＋RW＋RU20、RU40 | なし（動かない駒はいずれ隣に来られて取られる。時間の長さによらない） | 0 |
| （候補）RE＋RW＋ポケットの規則 | 7 枚（例: (0,1)〜(5,1) と (5,0)。7 枚すべてを使う 5 通りだけ） | 5 / 42,958,836 |

ポケットの規則は、RE の判定で相手の駒が届かない空きマスを空きとして数えないもので、ゲームには入れていない（静的な判定だけ、`search-exploit static --pocket-rule`。下の「所見」の 1(ii)）。

決めた形（人間の駒は七段目から始め、機械は台本どおりに動くか止まったまま）。各欄は「静的に取れない駒の数 ／ 攻略役が 90 秒で取った枚数（robust・seed）」。「作れない」は RW で壁になる形:

| 形 | R0 | RE | RE＋RW | RE＋RW＋RU20 | RE＋RW＋RU40 |
|---|---|---|---|---|---|
| 初期配置（一段目に 7 枚） | 7 ／ 0・0 | 0 ／ 7・7 | 作れない | 作れない | 作れない |
| 一段目の左端から 6 枚（7 枚目は (1,0)） | 7 ／ 0・0 | 0 ／ 7・7 | 0 ／ 7・7 | 0 ／ 7・7 | 0 ／ 7・7 |
| 二段目の壁 | 7 ／ 0・0 | 7 ／ 0・0 | 作れない | 作れない | 作れない |
| 二段目の左端から 6 枚＋(0,6)（壁の代わり） | 7 ／ 0・0 | 7 ／ 0・0 | 7 ／ 0・0 | 0 ／ 5・5 | 0 ／ 4・5 |
| 盤の中ほど（四段目）の壁 | 7 ／ 0・0 | 7 ／ 0・0 | 作れない | 作れない | 作れない |
| 四段目の左端から 6 枚＋(2,6) | 7 ／ 0・0 | 7 ／ 0・0 | 7 ／ 0・0 | 0 ／ 5・4 | 0 ／ 5・2 |
| ポケット（一段目の (0,1)〜(0,5)、(1,0)、(1,6)） | 7 ／ 0・0 | 7 ／ 0・0 | 7 ／ 0・0 | 0 ／ 4・4 | 0 ／ 4・4 |
| 一段目と二段目の往復（台本、下の注） | − ／ 4・4 | − ／ 7・7 | − ／ 7・7 | − ／ 5・7 | − ／ 5・5 |

- RE は、一段目に並べた形（初期配置、左端から 6 枚）を、人間が空きマスを 7 枚で埋めて丸ごと取れるようにした。しかし、人間が入れない空きマス（ポケット）を残した形と、二段目・中ほどの壁は残る。
- RW は壁を作れなくしたが、壁の端の 1 マスを空けて、その隣の段に 1 枚置けば同じ働きをする（壁の後ろの段がまるごとポケットになる）。ポケットの形は初期配置から 2 手（(0,0)→(1,0)、(0,6)→(1,6)）で作れ、その一手目は開始の一手として指せる。人間の側も同じ形（六段目と七段目の隅）を作れる。
- RU は動かない形をすべて崩した（攻略役は 90 秒で 2〜7 枚）。ただし、砦の駒を 20〜40 秒ごとに動かし直せば時計が戻る。台本の往復（下の注）は駒を順に一段目と二段目のあいだで動かす単純なもので、往復中の駒を挟まれてどのルールでも取られた。RU の下で、ポケットの駒を順に動かし直して守り続けられるかは、この確認では調べていない（学習の攻略役で確かめる）。
- 往復の台本: 一段目の (0,0)〜(0,5) と (1,6) から、1 枚を下ろしては前に下ろした 1 枚を上げる、を右端から左端へ、また右端へ（一段目は常に 5〜6 枚で、RW でも指せる）。読みではなく台本なので、機械は危なくても動く。

#### 所見と、候補を絞るための材料

- 砦: R0 は 4 枚で動かない砦が作れる（一段目の隅から 4 枚）。RE は一段目に並べた砦（初期配置と左端から 6 枚）をふさいだが、ポケットの形と壁が残る。RE＋RW は壁をふさいだが、壁の端の 1 マスを空けて隣の段で閉じる形とポケットの形が残り、最小は RE と同じ 4 枚、7 枚すべてを取られない形にもできる（初期配置から 2 手）。したがって第一候補の RE＋RW だけでは「こもって引き分け」はなくならない（人間の側も同じ形で、機械に 4 枚目を取らせない）。RU を加えると動かない砦はなくなる。
- 前進を強制した今の読みは、R0 の robust（3 局で平均 2.0 枚）を除き、どのルールでも攻略役に大きく負ける（(b)）。RE の下では、読みが端のまとまりを空きマスが 3 つ以下になるまで脅しとして読まない（`RACE_GROUP_MAX_FILL`）ため、人間が一段目の下を 1 枚ずつ埋めると逃げが間に合わず、まとめて取られる（RE＋RW の seed の局では、開始から 9〜15 秒で 4〜5 枚）。前進の重み 30 の読みも、seed の攻略役には開始からどのルールでも負け（(b)）、罠の配置からも取られる（下の注）。robust の攻略役には、60 秒までで R0 は 1.33 枚、RE＋RW は 2.67 枚。
- B1 との対局: 出荷の読み（重み 30）は、R0、RE、RE＋RW では B1 に 69〜83% 勝つが、外にいた割合は 11〜27% にとどまる。RE＋RW は R0 に比べて、局を 5.9 分から 4.0 分に縮め、引き分けを 8% から 2% に減らし、外にいた割合を 18% から 27% に上げた（つよい。開始の一手で一段目を出るため）。重み 120 では外にいた割合が 46〜52% になり、勝率は 37〜48% に下がる。RU の下では、今の読みは駒の放置時間を読まない（RaceTime の T_h に RU の脅しがない）ので、B1 に 2〜11%（RU20）、8〜28%（RU40）しか勝てず、局は 0.5〜1 分で終わる（RU の脅しを読むようにしたあとの数字は (d)）。
- 攻略されやすさは、ルールよりも読みの問題として残る。学習した読み（Step 1 以降）では、RE の端のまとまりの空きの数と、RU を採るなら駒ごとの放置時間を入力に入れる必要がある（3.6 のチャンネルに足す）。
- ユーザーが決めること（試遊を含む。2026-11-12 に 1 は (i) RU40 に決めた。3.1 の冒頭）:
  1. ポケットの砦をどうふさぐか。(i) RU を加える（RU40 は RU20 より B1 との局が長く、勝率の落ち方も小さい。ただし今の読みのままでは遊べないほど弱いので、RU を採るなら読みの直しか学習が前提。2026-11-07 の直しで B1 には RU40 で 58% 勝つようになったが、速い Race には 16〜19% にとどまる。(d)）。(ii) RE の判定で、相手の駒が届かない空きマス（ポケット）を空きとして数えない規則（以下「ポケットの規則」）を足す。ゲームには入れておらず、静的な判定だけで確かめた（`search-exploit static --pocket-rule`）: RE＋RW＋ポケットの規則では、決めた形はすべて取れるようになり、4 枚以上取られない形は 7 枚すべてを使う 5 通り（鏡像は1回）だけが残る（例: (0,1)〜(5,1) と (5,0) で (0,0)〜(4,0) を囲む形。人間が届く空きマスが 8 つあり、7 枚では埋めきれない）。採るなら Game・RaceTime・LED に足し、同じ表を作り直す。(iii) ルールではふさがず、報酬（3.3 の引き分けの罰と活動の制約）で機械にこもらせない（人間の側の砦は残る）。
  2. 試遊のすすめ: Web でルールを RE＋RW、RE＋RW＋RU40 に切り替え、「前進の重み」を 120 にして数局ずつ遊ぶ。ポケット（自陣の隅を1マス空けて閉じる形）を作ると機械が取れなくなること、RU では自分の駒を動かし続ける忙しさがあることを確かめ、面白さで選ぶ。
- 注（罠の配置）: 攻略役は、作り直し前の読みを相手に、罠 A〜D の配置（test_sim）のすべてから、ふつう・つよい、robust・seed のどれでも 20 秒以内に 2〜6 枚取った（`build/search-exploit traps`。`test/test_exploit` は、seed をふつう・つよいで、robust をつよいで、どの配置でも 1 枚以上取り、失った枚数より多いことを確かめる）。同じ攻略役（seed、つよい）は、今の読み（重み 30）からも D 以外の 6 つの配置で 2〜4 枚取った（作り直しのときの Trapper は決めた手順を変えないので逃げられていた）。再現: `build/search-exploit traps --mode seed|robust --level normal,hard --horizon 20 --per-plan 1`（今の読みは `--machine read --level hard`）。
- 限り: 攻略役の評価と候補の絞り方は手で決めたもので、取れないことの証明ではない（取れないことは静的な判定で示した）。robust の局は計算の都合で各 3 局（seed は各 6 局、重み 30 は各 3 局）、1 局 60 秒まで。B1 の考える時間と脅しの見落としの解釈は「方法」のとおりで、3.5 にはこれ以上の定めがない。

#### (d) RU の脅しを読む読み（2026-11-07）

ユーザーが RU を試遊し、つよいでも楽に勝てた。読みが自分の RU の取りしか数えず、自分の駒が放置になる脅しを読まないので、駒が放置されて取られる。そこで読み（`lib/core/Ai.cpp`、`lib/core/RaceTime.*`）に RU を足した。RU が入り（`untouchedMs > 0`）のときだけ働き、R0・RE・RW の読みと正解表は変わらない。

- RU の脅し: 機械の駒ごとに、人間が RU で取れる最短の時刻 = max(放置になるまでの時間, 縦横の空きマスのどれかへ人間の駒が置ける最短の時刻) を求める（`raceUntouchedTime`）。置ける時刻は 3.5 の e(h,s) と同じ（置く間隔、持ち上げ中と保留の規則、確保中のマスには置けない、強さごとの手順。やさしいは持ち上げ中の駒だけ）。隣が人間の駒なら、その駒がどいて別の駒か自分が入り直す（H3・H4）。隣の保留の置きは gap に着く。引いている途中の駒は取られない（`Snapshot::reservedId`）。
- 守りの割り当て: これを駒1枚の「RU の単位」として 3.7 に入れる。その駒をどこへ動かしても守れる（行き先は 3.6 の安全な行き先。時計は到着で戻る）。放置になるのが 15 秒以内の駒を単位にし、T_h が 15 秒未満なら危ない（`RACE_UNTOUCHED_DANGER_MS`。6 秒より長いのは、同時に放置になる駒を1枚ずつ順に動かし直す時間を読むため）。6 秒以上先で、ヘッドが今空いていても安全に動かせない駒は、後の読みに任せる（危ないに数えない）。駒を動かすと元のマスが隣の駒の空きマスになるので、隣の駒の RU も 3.6 (2) の残りに数える。1つの手が駒の列と RU の単位の両方を守れるときは、まとめて守ったものとする。
- 動かし直しの点: 守りの割り当てだけでは、駒を最後に動かそうとして、そのあいだに人間に逃げ道をふさがれた（自動対戦で多かった負け方）。そこで、空きマスに接する機械の駒ごとに、放置に近いほど点を引く（20 ×（1 − 残り ／ min(untouchedMs, 30 秒))、`STALE_WEIGHT`）。安全な手があるうちに、放置に近い駒から順に動かし直すようになる。重み 0・10・20・40、窓 20 秒・30 秒、危ないの範囲 10 秒・15 秒を各 100 局で比べて決めた（重み 0 では RU20・ふつう・B1 の勝率 18%、20 で 41%）。
- 攻めの見込み: 挟む相手の機械の駒が先に RU で取られる人間の列の gain は、3.7 の risk の式でその分だけ数えない。機械の到着までに放置になる人間の駒は RU で取れるものとする。人間の駒の放置に近づく手の gain も試したが入れていない: 3.8 のままでは、放置された駒はクールダウンがなく 450ms で逃げられるので見込みはほぼ 0 で何も変わらず（RU20・ふつう・B1 で 41% → 42%）、人間の反応を機械が動き出してからとすると前に出て取られ、悪くなった（41% → 20%）。
- 人間役ボット（Race、B1）、活動の指標、攻略役は RU の脅しを読まないまま（比べるため。`RaceTimes::untouched` を立てるのは読みだけ）。

B1 と Race（ボットの既定のまま: 置いてから 400ms で次を持ち上げ、考える時間と見落としなし）との対局。各条件 200 局（種 1〜200）、10 分打ち切り、前進の重み 30、ほかは既定値。「前」は直す前の読み（(c) の RU の行と同じ数字）。再現: `node tools/autoplay.mjs --games 200 --seed 1 --level normal,hard --bot b1,race --rules re+rw+ru20,re+rw+ru40`（前後の比べは `--baseline-out` と `--baseline`、同じ種どうしの対の差）。

### 3.2 取りの判定の一本化

- `Board::capturesAt` と、RaceTime の盤端の扱い（盤端に達する列を INF にしている箇所）を、`Rules` を受け取る1つの判定にまとめる（`lib/core/Capture.h/.cpp`。挟みと RE の両方を返す）。Game、Ai、RaceTime、HumanBot、LedPlan、SimDriver はすべてこれを使う。
- RaceTime は RE の下で、端のまとまりについて「人間が囲み終える時間」も見積もる（必要な空きマスを人間の駒が埋める時間を、今の H1〜H4 と同じ考え方で数える）。
- 正解表（AiCase）にルールの欄を足す。

### 3.3 目的（報酬と制約）

- 機械の報酬: 勝ち +1、負け −1、取った枚数の差が変わるたびに ±0.2。引き分けの罰は局の終わりにまとめず、取った枚数の差が0のあいだ毎秒 −0.5/600（10分続けば合計 −0.5）とする（割引で局の終わりの罰が消えるのを防ぐ）。
- 人間の報酬（人間の主役と攻略役）: 勝ち +1、負け −1、引き分け 0、取った枚数の差が変わるたびに ±0.2。ゼロ和にしない（ゼロ和にすると人間が引き分けで得をして、こもる人間役になるため）。
- 制約（ラグランジュ乗数つき PPO）: 現実的な人間役（固定の基準と人間の主役）との局でだけ数え、1分あたりに正規化する。
  - 機械の駒が自陣の段（一段目）の外にいた時間の割合。分母は、そのときまだ取られていない駒の数。
  - 機械が作った「取れる見込みのある脅し」の回数: 人間の駒の列（または RE の端のまとまり）について、RaceTime の取れる見込み（gain）が 0.5 以上になった回数。同じ列は、列の形が変わるまで1回と数える。
- 乗数は 0 から始め、学習率 0.01（制約の破れの平均に比例して増やす）、上限 10。制約ごとにコストの価値の出力を持ち、アドバンテージは報酬と同じ GAE で計算する。目標の値は Step 0 と Step 3 の測定のあとで決めて書く。
- 記録だけする指標: 機械の駒の平均の段、取りの回数と最初の取りまでの時間、引き分けの割合、1枚差以内で終わった局の割合、リードの入れ替わりの回数、同じ駒が往復した割合、序盤の手の多様さ、機械が動いた回数（1分あたり）。

### 3.4 学習用の環境

- C++ に「N 局をまとめて1回で進め、配列で返す」口を作る（`lib/core/BatchEnv`）。Python からは pybind11 で呼び、呼び出し中は GIL を外し、局をスレッドで並列に進める。観測、行動のマスク、報酬、制約のコスト、局の終わりをまとめて返す。
- 時間は 100ms 刻みで進め、記録する遷移は「その側に合法な行動が2つ以上ある決定点」だけにする（半マルコフ決定過程）。あいだの報酬はまとめる。割引は経過時間で γ^(Δt/τ)、半減期 120 秒（局の長さの約1/5。3.3 の毎秒の引き分けの罰と取りの報酬で、局の前半から行動に差がつく）。GAE の λ は 0.95。残り時間を入力に入れる。
- 機械の決定は、読みの間隔（`max(150, reactMs)`、毎回 ±50ms のゆらぎ）ごとにしか受け付けない。ファームの読みにも同じゆらぎを入れる。
- 決定が盤に効くまでの遅れ: 機械側は推論の時間（ESP32 の見積もり）、人間側は 0〜200ms（局ごとに無作為。実機の BoardWatcher の確定待ちと、Web で遊ぶ場合の両方を覆う）。SimDriver にも同じ遅れを入れられるようにする。
- 同じ刻みで両者の行動がぶつかったときの処理の順は、学習中は毎回無作為に選ぶ。
- （2026-11-10）電磁石の発熱を実測したら、電磁石のデューティか連続通電の上限をゲームのパラメータにし、シミュレータはそれを模して、学習ではばらつかせる。
- 毎局、機械の速さ（空送り、引く速さ、吸着時間 ±30%）、読みの間隔（150〜350ms）、人間の手の速さと観測の遅れ（3.5）、強さの段階のための反応の遅れ（0〜300ms）と速さの上限をばらつかせる。機械の速さと自分の反応の遅れ・速さの上限は機械の入力に見せる。人間の速さは見せず、直近の人間の手の時間（3.6）から推し量らせる。
- ルールは学習の段階に応じて固定する（Step 0 で残った候補。Step 4 の短い比較だけ、ルールを入力に入れて候補をまたいで学習する）。

### 3.5 人間役

- 行動の意味: 「何もしない」「持ち上げる（駒のマス）」「置く（マス）」。持ち上げ中に元のマスへ置くのは取り消し。持ち上げ上限（1秒）までに置かなければ、ルールどおり元のマスへ戻りクールダウンが付く。保留はルールどおり。持ち上げ中は「持ち上げる」は選べない。
- 観測の遅れ: 機械の駒、ヘッド、機械のジョブの情報だけを 200〜500ms（局ごとに決め、毎回 ±50ms）遅らせる。自分の手の内（持っている駒、保留、自分のクールダウン、置く間隔）は遅らせない。行動のマスクは、遅れた機械の情報と今の自分の情報から作る。実行した時点で不合法なら、その行動は失敗として扱う（Game の結果をそのまま使う）。
- 1手の時間は、毎手、移動距離に応じた分布から引く。対局記録（3.12）が集まるまでは暫定（平均 0.5 秒＋距離あたり 0.05 秒、対数正規、ばらつき 0.3）。
- 固定の基準の人間役（目標の勝率と受け入れの判定に使う。学習で変えない）:
  - B1: 手書きのボットに考える時間（1〜3 秒）と、脅しの見落とし（確率 0.3）を足したもの。
  - B2: 対局記録から作った模倣モデル（記録が 50 局以上集まってから。足りないあいだは B1 だけ）。
  - B3: 模倣の事前分布（B2、なければ手書きのボットを模倣したモデル）への KL の罰を強さ 1.0 で付けて学習し、固定した人間役（piKL、Jacob ほか ICML 2022）。
- 人間の主役: 3.5 の制約を守って学習する人間。機械の相手として使い、B3 と同じ KL の罰を付ける（強さは学習の設定で 0.1〜1.0）。
- 攻略役: 観測の遅れと手の時間の下限だけを守り、KL の罰なしで勝つことだけを目指す。上限を測るためだけに使う。

### 3.6 入力（観測）

- 入力の組み立ては C++（`lib/core/Features.h/.cpp`）に置き、ファーム・WASM・学習で同じものを使う。値は整数で作る。盤は 7×7 に固定する。
- チャンネル（機械用）: 自分の駒、相手の駒、持ち上げ中の駒の元のマス、保留先、確保中のマス、駒ごとのクールダウンの残り、置く間隔の残り、持ち上げの経過時間、ヘッドの位置、動かしている駒と行き先、運び出しの段階、取った枚数と残り時間、Opening かどうかと各側が指し終えたか、ルールの値、機械の速さ、自分の反応の遅れと速さの上限、直近の人間の手の時間（3回分の平均）。盤全体の量は盤全体に同じ値を入れる。
- RaceTime の見積もりは、入れる版と入れない版を Step 4 で比べる。入れる場合は、各列の「人間が挟み終える時間 − 機械が避け始める時間」を −2000〜+2000ms の16段階の整数に丸め（INF は端の値）、その列の駒のマスに置く。1つの駒が2つの列に入るときは小さいほう（危ないほう）を置く。
- 人間用の入力も同じ形（自分と相手の意味を入れ替え、機械の速さは除く）。

### 3.7 出力（行動）

- 機械: 平らな出力「元のマス × 方向（4）× 距離（1〜6）」（49×24、1×1 の畳み込み）と「動かない」の1つ。合法でない手は大きな負の値にする。同点は番号の小さい手。
- 人間: 「何もしない」、持ち上げる駒のマス（49）、置くマス（49）。持ち上げ中かどうかで使う出力を切り替える。
- 機械用と人間用のネットは別に持つ。鏡像の水増しは使わない。

### 3.8 ネットワークと整数の推論

- 大きさは ESP32（240MHz、SIMD なし）の命令数で決める。予算は読み1回の全体（入力の組み立て、RaceTime、推論）で 30ms、命令数の見積もりに 1.5 倍の余裕を見る。暫定の形: 入力の 3×3 畳み込み → 残差ブロック2つ（16 チャンネル）→ 出力（約 0.65M 回の積和）。
- `Net.cpp` は `#pragma GCC optimize("O2")` で最適化の水準を上げる（Arduino-ESP32 は既定で -Os でビルドし、-Os では内側のループが約10命令/積和、-O2 で約5命令になる）。命令数は、ファームのビルドで出る `firmware.elf` を逆アセンブルして数える。ESP32 が届いたら実測する。
- 重みは int8 の範囲の値を int16 で持ち、活性は int16、累積は int32。書き出しのときに、各層で最悪の場合の累積の絶対値が 2^31 未満になることを確かめる（超えれば倍率を下げる）。再量子化は `(x * m + (1 << (s − 1))) >> s` を int64 で計算し（算術右シフト）、int16 に飽和させる。残差の足し算の前に2つの枝の倍率を揃える。ESP32 では重みを起動時に DRAM へ写す。
- Python の基準の推論は、C++ と同じ整数の計算を NumPy で書く。正解表は手とロジットを比べる。
- 手の選び方: 段階に応じた温度で、Snapshot から作るハッシュを種にした整数の疑似乱数と整数のノイズによる Gumbel-max で選ぶ（3環境で同じ手）。局ごとの種を変え、同じ手順で同じ罠が再現しないようにする。
- 量子化した方策そのものの成績と攻略されやすさを測る。足りなければ量子化を意識した学習で補う。

### 3.9 学習

- 手順:
  1. 模倣学習: 機械のネットを今の時間の競争の読み（Step 0 で選んだルールに合わせたもの）から、人間のネットを手書きのボットと B1 から学習する。
  2. PPO: 環境の数 256、1回に集める長さ 128 決定点、エポック 4、ミニバッチ 4096、クリップ 0.2、学習率 3e-4（線形に下げる）、エントロピーの罰 0.01、価値の誤差の重み 0.5、勾配の上限 0.5。参照方策への KL の罰（係数 0.05、参照方策は 5000 万ステップごとに今の版へ更新）。制約は 3.3。
  3. 小さなリーグ: 同時に学習するのは機械の主役、人間の主役、主役を攻略する人間役の3体。機械の相手は2段の混合で選ぶ: 60% を固定の基準の人間役と人間の主役（半々）、20% を手書きのボット、20% を PFSP（人間の主役の過去の版と攻略役）。攻略役は 1 億ステップごとに作り直し、機械が攻略役に負け越していたら、その攻略役を PFSP の相手に加える。
  4. PFSP: 勝率 x の相手を (1 − x)² に比例して選ぶ（引き分けは 0.5 勝）。
  5. リーグを大きくする判断: 探索と学習の攻略役で弱点が残ると測れたときに、攻略役の数を増やす。
- 価値の出力には、学習中だけ相手の種類を入力に加える。
- 学習量の見当: C++ でまとめて回せば全体で毎秒 1〜4 万ステップ。手書きのボットに勝ち越すまで数千万ステップ、リーグと攻略役を含めると 10 億ステップの桁で数日。

### 3.10 学習を行う場所と、結果の受け渡し

- 開発はクラウドのセッション、本番の学習はデスクトップの WSL2 の Ubuntu。
- デスクトップの準備: リポジトリは Ubuntu のホーム（`/mnt/c` ではない）に置く。GPU は Windows 側の NVIDIA ドライバーを WSL2 から使い、Ubuntu の中に Linux 用のドライバーは入れない。PyTorch は venv に CUDA 版を入れる。学習は tmux の中で回し、Windows のスリープと自動再起動を止める。
- `scripts/train-desktop.sh` に、依存の導入、C++ のつなぎのビルド、学習の開始と再開、評価、書き出しをまとめる。使う論理プロセッサの数（既定は半分）と優先度（`nice`）を引数で指定できる。作業ツリーに変更が残っていると学習を始めない。
- 学習の実行ごとに、設定とコミットのハッシュを入れたディレクトリを作る。チェックポイント（ネットと最適化の状態、リーグの全版、PFSP の成績表、乱数の状態）はそこに置く。
- 各実行には予算（ステップ数か時間）と、止める条件・見直す条件を設定ファイルに書く（例: 2000 万ステップで手書きのボットへの成績が今の読みを下回っていれば止めて見直す）。
- 学習の終わりに、デスクトップで `evaluate.py` を回して 3.15 の指標を出し、最後の float のネット、量子化の設定、学習の設定、コミットのハッシュ、`lib/core/NetWeights.h`、評価の結果を書き出してプッシュする。クラウドは推論の一致を確かめ、評価を抜き取りで確かめる。

### 3.11 評価

- 学習に使わない相手（受け入れの判定）: 何もしない人、ためらう人（1手 1〜2 秒、ときどき何もしない）、初心者らしいランダムな人、手の時間を変えた Trap・Race・Race3、固定の基準の人間役 B1〜B3。
- 探索による攻略役（PC だけ、`tools/search-exploit`）: 人間の1手を単位にしたビーム探索。手の単位は（持ち上げる駒、置くマス、待ち {0, 250, 500, 1000ms}）、ビームの幅 64、深さ 6 手、途中の局面は RaceTime を使った評価（取った枚数の差＋取れる見込み）で比べる。決定的な先読みにならないよう、候補の手順は機械の種 K=8 個と、人間の手の時間・観測の遅れ・機械の速さのゆらぎで平均して採点する（ゆらぎに強い攻略）。種に依存する数字とゆらぎに強い数字の両方を出し、受け入れの上限はゆらぎに強いほうで決める。
- 学習による攻略役: 人間の主役から始めて微調整し、種を3つ以上使い、学習量に対する曲線で報告する。指標は取った枚数の差の期待値。
- 比較は種ごとの対とブートストラップの信頼区間。
- ユーザーの試遊: どちらの読みかを伏せた A/B で、同じ人が数回遊び、面白さと、繰り返し使える罠が見つかったかを記録する。

### 3.12 対局の記録

- Web のシミュレータに記録を足す: ルールと設定、読みの種類と強さ、人間の操作（持ち上げと置きの時刻、マス、結果）、機械の手、取り、勝敗。
- 手元の `npm run serve` では serve.mjs に送り、`logs/`（git に入れない）に JSON Lines で保存する。公開ページでの保存先は、Artifact の実行時の機能で使えるものを Step 3 で確かめて決め、使えなければクリップボードにコピーするボタンを付ける。
- 個人を特定する情報は入れない。

### 3.13 強さの段階

最後の版に、反応の遅れ、温度、速さの上限で差をつける（いずれも学習中にばらつかせて入力に見せた範囲の中で）。各段階が、固定の基準の人間役に対して目標の勝率（やさしい2〜3割、ふつう5割、つよい7割以上）に入るように調整する。最後の確認はユーザーの A/B 試遊。

### 3.14 安全の確認

推論の手を RaceTime で拒否する仕組みは入れない。評価の診断（危ないとされる手をネットがどれだけ選び、実際に取られたか）にだけ使う。

### 3.15 受け入れ条件

- 固定の基準の人間役に対して、各段階が目標の勝率に入る。
- 活動の指標が目標以上（目標は Step 0 と Step 3 のあとで決めて書く）。何もしない人とためらう人に対して、機械が自分から攻めて取る（選んだルールの下で、1局あたり平均2枚以上）。引き分けは 10% 以下。
- 探索による攻略役（ゆらぎに強い数字）が、つよいから取れる枚数の期待値が、決めた上限以下（上限は Step 0 のあとで決める）。
- 正解表で、PC・WASM の推論のロジットが Python の基準と一致する。ESP32 は命令数の見積もりで 30ms 以内（届いたら実測し、ESP32 との一致もそのとき確かめる）。
- ユーザーの A/B 試遊で、今の読みより面白いと判断される。

## 4. 変えないもの・範囲外
