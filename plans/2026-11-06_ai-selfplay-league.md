# ソフトウェア計画: 面白い機械を目指して、ルールと読みを学習で作り直す

2026-11-06（同日、専門家レビューとユーザーの判断を受けて全面改訂）/ 対象: 機械の読み（`Ai::think`）を自己対戦の強化学習で学習した小さなネットに置き換えること、その前提となるルールの候補の比較、学習の環境（C++ コアを Python から呼ぶ）、整数だけの推論（ESP32・WASM・PC で同じ手）、現実的な人間役、面白さと攻略されにくさの測り方、対局の記録。`plans/2026-10-31_ai-time-race.md` の時間の見積もり（RaceTime）と時間の競争の読みは、学習した読みが仕上がるまで既定の読みとして残す。

## 1. 背景

### 1.1 これまでに起きたこと

2026-10-31 の時間の競争による作り直しで、ボット相手に失う枚数は1局あたり約4枚から約1.2〜2.3枚に減った。ところが 2026-11-06、機械がほとんど自分から動かないことがわかった。前進の点の重みを上げると30秒で2〜3手は動くが、失う枚数はすぐ約3.7枚に戻る（つよい対 Race、100局）。何もしない人間を相手にすると、2分間一度も動かない。動いても、機械の駒の平均の段は0.7〜0.8で、一段目の外にいるのは平均1.5〜2.1枚だった。

### 1.2 原因（専門家レビューの結論）

受け身の原因は、読みの弱さではなく、ゲームの決まりと目的にある。機械の初期配置（一段目に盤端から盤端まで並んだ一列）は、盤端に達する列は取らない規則のため一枚も取られない。動かなければ失わず、負けない。人間が2枚で挟むのにかかる時間（置く間隔1秒の下で約1.5秒）と、機械が気づいて引き始めるまでの時間（約1秒以上）の差もある。このまま「勝ち負け」を目的に学習させると、強化学習も「動かずに引き分け」を、前の読みよりも確実に見つけるだけになる。

### 1.3 ユーザーの判断（2026-11-06）

- 目的は「遊んで面白い機械」。攻略されにくさは、楽勝されないための最低限の条件にとどめる。
- 面白くできるなら、ルールに要素を足してよい。
- 強さの目安は、現実的な人間を相手に、やさしい2〜3割、ふつう5割、つよい7割以上の勝ち。
- Web のシミュレータで遊んだ対局を記録し、人間役の調整に使ってよい。
- 学習は家のデスクトップ（Windows＋WSL2 の Ubuntu、Ryzen 7 5700X 8コア16スレッド、RTX 4060 8GB）で、ほかの作業と並行できる範囲で何日でも回してよい。
- ESP32 の開発ボードはまだ手元にない。

### 1.4 方式の選択

| 方式 | 判断 |
|---|---|
| 手書きの見積もりと点数（今の読み） | 単独では打ち切る。学習の入力の候補と、模倣学習の出発点に使う |
| AlphaZero・MuZero 型の探索 | 同時手番・実時間に合わず ESP32 で探索できないので配る方式にはしない。PC での攻略役（3.10）に探索を使う |
| AlphaStar 型のリーグ（全部入り） | 機械と人間の両側に主役・攻略役をすべてそろえる構成は、このゲームと RTX 4060 1枚には重い。学習するのは3体（機械の主役、人間の主役、主役を攻略する人間役）の小さなリーグにし、攻略されやすさの数字を見て役を足す |
| 自己対戦の強化学習（PPO）＋参照方策への KL 正則化 | 採用。自己対戦の発散を抑える magnetic mirror descent（Sokota ほか ICLR 2023、DeepNash の R-NaD と同じ系統）を使う |
| 模倣学習からの出発 | 採用。今の読み（機械）と手書きのボット（人間）を真似したネットで、量子化から ESP32・Web までを先に一本通す |
| 制約つき強化学習 | 採用。面白さ（活動）を報酬の足し算ではなく制約として扱う（ラグランジュ乗数つき PPO）。報酬に活動の点を足すと駒の往復で稼がれるため |

## 2. 目的と方針

- 機械の目的は、現実的な人間を相手に、強さの段階ごとの目標の勝率に入り、かつ自分から前に出て脅しと取りを作ること（3.2）。攻略されにくさは、探索による攻略役に楽勝されないことを上限の条件にする（3.10）。
- 学習の前に、ルールの候補（砦をなくすもの）を小さな実験で比べ、候補を絞ってからユーザーが決める（Step 0）。本番の学習は、決めたルールで行う。
- 人間役は「現実的な人間役」（機械が主に戦う相手。観測の遅れ、手の時間のばらつき、対局記録への寄せ）と「攻略役」（上限を測るためだけ）に分ける。
- ゲームの規則と時間の進み方は今の C++ コアをそのまま使い、学習・シミュレータ・ファームで食い違わないようにする。学習の入力の組み立ても C++ に置く。
- ネットは整数だけで推論し、3環境でロジットまで一致させる。ネットの大きさは ESP32 の命令数の見積もりで先に決め、開発ボードが届いたら実測で確かめる。
- 学習した読みは設定で切り替えられるようにし、仕上がるまでは今の読みを既定にする。

## 3. 仕様

### 3.1 ルールの候補（Step 0 で比べる）

- R0: 今のルール（基準）。
- R1: 自陣の保護の時間切れ。自分の初期の段（機械は一段目、人間は七段目）に続けて T 秒（候補 20／40 秒）いる駒は、その段にいるあいだ盤端の保護を失う（盤端に達する列でも、反対側を相手の駒にふさがれれば取られる）。人間と機械に同じく適用する。
- R2: 時間切れの判定に前進を入れる。10分で取った枚数が同じなら、相手陣の側にいた時間の合計が長いほうの勝ち。
- R3: 隅の囲み取りを認める（伝統的なはさみ将棋の変則ルールの一つ。隅の駒は、隣接する2マスを相手が占めれば取られる）。
- R1〜R3 の組み合わせも候補にする。
- 比べ方（Step 0）: 各候補で、(a) 前進を強制した今の読みの機械に対して、PC の探索による攻略役（3.10）が取れる枚数、(b) 現実的な人間役のボット（3.4 の暫定版）との対局の活動の指標（3.2）、(c) 1局の長さと引き分けの割合、を表にする。数字で2〜3に絞り、Web で切り替えて遊べるようにして、ユーザーが決める。

### 3.2 目的（報酬と制約）

- 報酬: 局の終わりに勝ち +1、負け −1、引き分け −0.5（機械にとって引き分けは負けに近い）。途中の報酬として、取った枚数の差が変わるたびに ±0.2（取りはほぼ勝敗に直結するので、学習の途中でも下げない）。
- 制約（ラグランジュ乗数つき PPO）: 局ごとに次の値が目標以上になるようにする。目標は Step 0 と Step 3 の測定のあとで決め、計画に書く。
  - 機械の駒が一段目の外にいた時間の割合（全駒の平均）。
  - 機械が自分から作った脅し（人間の駒の列に対して、機械が1手で挟める形になった回数。同じ列への脅しは、列の形が変わるまで1回と数え、往復では増えにくくする）。
- 活動の指標として記録し、制約には使わないもの: 機械の駒の平均の段、取りの回数と最初の取りまでの時間、引き分け・時間切れの割合、1枚差以内で終わった局の割合とリードの入れ替わりの回数、同じ駒が往復した割合、種を変えたときの序盤の手の多様さ、機械が動いた回数（1分あたり）。

### 3.3 学習用の環境

- C++ に「N 局をまとめて1回で進め、配列で返す」口を作る（`lib/core/BatchEnv`）。Python からは pybind11 で呼び、呼び出し中は GIL を外し、局をスレッドで並列に進める。観測、行動のマスク、報酬、制約の値、局の終わりをまとめて返す。
- 時間は 100ms 刻みで進めるが、記録する遷移は「その側に合法な行動が2つ以上ある決定点」だけにする（半マルコフ決定過程）。あいだの報酬はまとめる。割引は経過時間で γ^(Δt/τ)、半減期 30 秒から試す。GAE の λ は 0.95。
- 機械の決定は、読みの間隔（`max(150, reactMs)`、毎回 ±50ms のゆらぎ）ごとにしか受け付けない。ファームの読みにも同じゆらぎを入れる（人間に位相を読まれないため）。
- 決定が盤に効くまでの遅れとして、機械側は推論の時間（ESP32 の見積もり）、人間側は BoardWatcher の確定待ち（200ms、実機の場合）を環境に入れる。シミュレータ（SimDriver）にも同じ遅れを入れられるようにし、PC・WASM と実機で局の進み方を揃える。
- 同じ刻みで両者の行動がぶつかったときの処理の順は、学習中は毎回無作為に選ぶ（今の SimDriver は機械が先）。
- 毎局、機械の速さ（空送り、引く速さ、吸着時間 ±30%）、読みの間隔（150〜350ms）、人間の手の速さと反応の遅れ（3.4）をばらつかせる。機械の速さは機械の入力に見せる（実機では既知）。人間の速さは見せず、直近の人間の手の時間（3.5）から推し量らせる。

### 3.4 人間役

- 行動の意味: 「何もしない」「持ち上げる（駒のマス）」「置く（マス）」。持ち上げ中に元のマスへ置くのは取り消し。持ち上げ上限（1秒）までに置かなければ、ルールどおり元のマスへ戻りクールダウンが付く。保留（置く間隔より早い置き）はルールどおり。
- 現実的な人間役:
  - 観測は 200〜500ms（局ごとに決め、毎回 ±50ms）遅れた盤。行動のマスクも遅れた盤から作る。実行した時点で不合法なら、その行動は失敗として扱う（Game の結果をそのまま使う）。
  - 1手の時間（持ち上げから置くまで）は、毎手、移動距離に応じた分布から引く。分布の形は、対局記録（3.11）が集まるまでは暫定（平均 0.5 秒＋距離あたり 0.05 秒、対数正規）。
  - 対局記録が集まったら、記録から学習した模倣モデルを作り、方策に模倣モデルへの KL の罰を付ける（piKL、Jacob ほか ICML 2022）。
- 攻略役: 観測の遅れと手の時間の下限だけを守り、勝つことだけを目指す。機械の弱点の上限を測るためだけに使い、機械の主な学習相手にはしない（選ぶ重みを小さくする）。

### 3.5 入力（観測）

- 入力の組み立ては C++（`lib/core/Features.h/.cpp`）に置き、ファーム・WASM・学習で同じものを使う。値は整数で作る。
- 盤は 7×7 に固定する（学習した読みは 7×7 のときだけ使う）。
- チャンネル（機械用）: 自分の駒、相手の駒、持ち上げ中の駒の元のマス、保留先、確保中のマス、駒ごとのクールダウンの残り、置く間隔の残り、持ち上げの経過時間、ヘッドの位置、動かしている駒と行き先、運び出しの段階、取った枚数と残り時間（盤全体に同じ値）、自陣にいる時間（R1 のため）、ルールの値（Step 0 で残した候補を表すもの）、機械の速さ、直近の人間の手の時間（3回分の平均を盤全体に）。
- RaceTime の見積もり（各列の、人間が挟み終える時間と機械が避け始める時間の差）は、入れる版と入れない版を Step 4 で比べる。入れる場合は、差を整数のバケツ（−2000〜+2000ms を 16 段階、INF は端の値）に丸めてから、その列の駒のマスに置く。
- 人間用の入力も同じ形（自分と相手の意味を入れ替えたもの、機械の速さは除く）。

### 3.6 出力（行動）

- 機械: 平らな出力「元のマス × 方向（4）× 距離（1〜6）」（49×24、1×1 の畳み込みで出す）と「動かない」の1つ。合法でない手はロジットを大きな負の値にする。同点は番号の小さい手。
- 人間: 「何もしない」、持ち上げる駒のマス（49）、置くマス（49）。持ち上げ中かどうかで、使う出力を切り替える。
- 機械用と人間用のネットは別に持つ。左右の鏡像による学習データの水増しは、手の順や同点のハッシュが左右対称でないので使わない。

### 3.7 ネットワークと整数の推論

- 大きさは、ESP32（240MHz、SIMD なし）の命令数の見積もりで決める。レビューの確認では、int8 の素直な実装は1積和あたり8命令、int16 で MAC16 命令を使うと5命令。読みの時間の予算を 30ms 以内とすると、積和は約 1.2M 回まで。暫定の形: 入力の 3×3 畳み込み → 残差ブロック2つ（16 チャンネル）→ 出力（約 0.65M 回の積和、約 13ms の見込み）。Step 2 で xtensa の GCC の出力から命令数を数えて確かめ、開発ボードが届いたら実測する。
- 活性と重みは int16、累積は int32。再量子化は `(x * m + (1 << (s − 1))) >> s`（算術右シフト）で、結果は int16 の範囲に飽和させる。残差の足し算の前に、2つの枝の倍率を揃える。ESP32 では重みを起動時に DRAM へ写す。
- Python 側の基準の推論は、C++ と同じ整数の計算を NumPy で書く（PyTorch の疑似量子化は使わない）。正解表は、手だけでなくロジットを比べる。
- 手の選び方: つよいは低い温度、やさしいとふつうは段階に応じた温度で、Snapshot から作るハッシュを種にした整数の疑似乱数と、整数のノイズによる Gumbel-max で選ぶ（3環境で同じ手）。局ごとの種を変えることで、同じ手順で同じ罠が再現しないようにする（種を渡せば再現できる）。
- 学習後の量子化で、量子化した方策そのものの成績と攻略されやすさを測る（手の一致率だけでは判断しない）。足りなければ量子化を意識した学習で補う。

### 3.8 学習

- 手順:
  1. 模倣学習: 機械のネットを今の時間の競争の読みから、人間のネットを Race・Race3・現実的な人間のボットから学習する。
  2. PPO（クリップ 0.2、学習率 3e-4 から、行動マスク、エントロピーの罰 0.01、価値の誤差の重み 0.5）。参照方策（直前の段階の版）への KL の罰（magnetic mirror descent）を付ける。制約はラグランジュ乗数で扱う（3.2）。
  3. 小さなリーグ（同時に学習するのは3体。PSRO に近い形）: 機械の相手は、現実的な人間役（主）、手書きのボット、人間の主役の過去の版。人間の主役は機械の過去の版と戦う。一定の学習量ごとに攻略役を作り直し、機械が攻略役に負け越したら、その攻略役を相手の集まりに加える（重みは小さく）。
  4. 相手の選び方は PFSP（勝率 x の相手を (1 − x)² に比例して選ぶ。引き分けは 0.5 勝）。
- 価値の出力には、学習中だけ相手の種類を入力に加える（配るときは使わない）。
- リーグを大きくする判断: 探索と学習の攻略役で弱点が残ると測れたときに、攻略役の数を増やす（最初から役を増やすと、1体あたりの学習量が減ってどれも中途半端になりやすいため）。
- 学習量の見当（レビューの見積もり）: C++ でまとめて回せば全体で毎秒 1〜4 万ステップ。手書きのボットに勝ち越すまで数千万ステップ、相手の集まりと攻略役を含めると 10 億ステップの桁で数日。デスクトップの作業と並行できるように、使う論理プロセッサの数を指定でき（既定は論理プロセッサの数の半分）、優先度を下げて動かす。

### 3.9 学習を行う場所と、結果の受け渡し

- 開発（環境、入力、推論、評価の道具、組み込み、テスト）はクラウドのセッションで行い、クラウドでは CPU で小さな学習量だけ確かめる。本番の学習はデスクトップの WSL2 の Ubuntu で行う。
- デスクトップの準備: リポジトリは Ubuntu のホーム（`/mnt/c` ではない）に置く。GPU は Windows 側の NVIDIA ドライバーを WSL2 から使い、Ubuntu の中に Linux 用のドライバーは入れない。PyTorch は仮想環境（venv）に CUDA 版を入れる。学習は tmux の中で回し、Windows のスリープと自動再起動を止めておく。
- お手元の手順は `scripts/train-desktop.sh` 1つにまとめる（依存の導入、C++ のつなぎのビルド、学習の開始と再開、記録の書き出し）。使う論理プロセッサの数と優先度を引数で指定できる。
- 再開に必要なもの（ネットと最適化の状態、相手の集まりの全版、PFSP の成績表、乱数の状態）をチェックポイントに保存する。
- 結果の受け渡し: 学習の終わりに、最後の float のネット、量子化の設定、学習の設定、学習に使ったコミットのハッシュ、量子化した重みのヘッダ（`lib/core/NetWeights.h`）、学習の記録の要約を書き出し、ブランチにコミットしてプッシュする（ネットは数十KB、版を残しても数MB なのでリポジトリに入れる）。クラウドのセッションはそれを使って推論の一致と評価を行う。

### 3.10 評価

- 学習に使わない相手（受け入れの判定に使う）: 何もしない人、遅い人（1手 1〜2 秒）、初心者らしいランダムな人、手の時間を変えた Trap・Race・Race3、対局記録から作った模倣モデルの人間役。
- 探索による攻略役（PC だけ）: 機械とシミュレータは決定的なので、局ごとのパラメータを固定すれば、人間側の最善の応じ方は一人用の計画問題になる。人間の1手を単位にしたビーム探索（または MCTS）で、観測の遅れと手の時間の下限を守ったまま、機械から最も多く取れる手順を探す。指標は取った枚数の差の期待値。
- 学習による攻略役: 相手の集まりでいちばん強い人間役から始めて微調整し、種を3つ以上使い、学習量に対する曲線で報告する。
- 比較は種ごとの対とブートストラップの信頼区間（2026-10-31 の計画の道具）。
- ユーザーの試遊: どちらの読みかを伏せた A/B で、同じ人が数回遊ぶ。面白さの評価と、繰り返し使える罠が見つかったかを記録する。

### 3.11 対局の記録

- Web のシミュレータに対局の記録を足す: ルールと設定、読みの種類と強さ、人間の操作（持ち上げと置きの時刻、マス、結果）、機械の手、取り、勝敗。
- 手元で `npm run serve` で遊ぶときは、記録を serve.mjs に送り、`logs/`（git に入れない）に JSON Lines で保存する。
- 公開ページで遊ぶときの保存先は、Artifact の実行時の機能で使えるもの（共有のデータベースなど）を Step 3 で確かめて決める。使えない場合は、記録をクリップボードにコピーするボタンを付ける。
- 記録は、人間役の手の時間の分布（3.4）と模倣モデルに使う。記録の中に個人を特定する情報は入れない。

### 3.12 強さの段階

最後の版に、反応の遅れ、温度、速さの上限で差をつける。各段階が、学習に使わない現実的な人間役（3.10）に対して、目標の勝率（やさしい2〜3割、ふつう5割、つよい7割以上）に入るように調整する。

### 3.13 安全の確認（RaceTime による拒否）

推論の手を RaceTime で拒否する仕組みは入れない。評価の診断（危ないとされる手をネットがどれだけ選び、実際に取られたか）にだけ使う。必要になった場合は、「到着した時点で人間が1手で取れる」確実な脅威だけを、学習の環境にも同じく入れて使う。

### 3.14 受け入れ条件

- 学習に使わない現実的な人間役に対して、各段階が目標の勝率に入る。
- 活動の指標が目標以上（目標は Step 0 と Step 3 のあとで決めて書く）。何もしない人と遅い人に対して、機械が自分から攻めて取る（1局あたり平均2枚以上）。引き分けは 10% 以下。
- 探索による攻略役が、つよいから取れる枚数の期待値が、決めた上限以下（上限は Step 0 のあとで決める）。
- 正解表で、PC・WASM の推論のロジットが Python の基準の推論と一致する。ESP32 は命令数の見積もりで 30ms 以内（開発ボードが届いたら実測で確かめ、ESP32 との一致もそのとき確かめる）。
- ユーザーの A/B 試遊で、今の読みより面白いと判断される。

## 4. 変えないもの・範囲外

- 運び出し、LED の色規則、ファームの構成（読みの呼び出し口、読みの時刻のゆらぎ、推論の遅れの扱いだけ変える）。
- 9×9 での学習した読み。
- ルールの最終決定（Step 0 で数字を出し、ユーザーが遊んで決める）。
